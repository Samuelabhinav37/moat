moat · content-blocking internals · v0.11.63

How Moat hides ads

Moat is a Manifest V3 ad and tracker blocker for Chrome and Firefox. Network requests are killed by the browser itself; the leftover empty boxes are hidden by filter-list selectors. This is how that second half works — and why, since v0.11.63, the service worker parses the selector dataset instead of the page.

01

Two engines, one hot path

Blocking an ad happens in two unrelated places.

Network blocking is pure declarativeNetRequest. Moat ships 271,270 static DNR rules across 20 rulesets, compiled from 11 AdGuard lists plus three first-party ones. The browser loads that index once at install and matches every outgoing request against it in native code. There is no Moat JavaScript on this path — nothing to profile, nothing to optimise. A request to a known ad host simply never leaves the browser.

Cosmetic filtering is the part with actual runtime cost. When a page reserves a 300×250 slot, drops in an <iframe>, and the iframe request is blocked, the slot stays — an empty gap, sometimes with a “advertisement” label above it. Cosmetic rules are CSS selectors (AdGuard’s ## syntax) that hide those containers. Applying them means running Moat code in the page, on every navigation.

So the whole performance story is the cosmetic engine. Everything below is about keeping it cheap.

02

What cosmetic hiding is up against

Cosmetic selectors come in two kinds, and they scale very differently.

Domain-scoped selectors are tied to a hostname: example.com##.promo-rail. Moat carries 138,392 of them across 52,776 domains. For any given page only a handful apply, so the cost is finding this page’s handful quickly.

Generic selectors have no hostname — .ad-slot, .sponsored-post, [data-ad-unit] — and are meant to fire everywhere. There are about 17,100 of them. Injecting all 17k as one stylesheet on every page is what a naive blocker does, and it makes the browser’s style engine evaluate 17,000 selectors against every DOM mutation for the life of the page.

The generic-selector split

Moat divides the generic set by whether a selector has an anchoring token — a class or id that must be present for it to match anything:

SliceCountWhen it’s injected
genericHigh1,068Up front, every page — no usable anchor ([data-ad], div > .x)
genericByHash16,080Only once its anchor token is seen in the DOM — filed under 14,792 token buckets

The bet: on a real page, only dozens of those 14,792 tokens ever appear, so the style engine only ever evaluates the few dozen generic selectors that could plausibly match. A DOM surveyor watches for the tokens and asks for their selectors as they show up.

03

How the lists become an index

At build time, scripts/update-cosmetics.mjs parses the raw AdGuard lists and emits:

  • cosmetics-meta.json — ~684 KB (~215 KB gzipped). Holds genericHigh, the genericByHash map, all 5,768 exceptions (domain#@#selector), and the 5 generic CSS-injection rules.
  • cosmetics-bucket-0.json … -63.json — the 138k domain-scoped selectors, sharded into 64 files by a hash of the registrable domain so a page fetches ~1–3 small files, not one 6 MB blob.
  • cosmetics-manifest.json — 47 bytes: the meta filename and the bucket count.

The token hash is FNV-1a, emitted as a base-36 string so it’s a compact JSON key. It has a byte-identical twin in scripts/lib/tokenHash.mjs, parity-checked in CI — the build files a selector under a token’s hash, and the runtime hashes the tokens it finds; the two never communicate, so they must compute the same value. Same discipline as the 64-way domain bucketing (bucketForDomain, also FNV).

04

One navigation, step by step

The cosmetic content script runs at document_start in the top frame only. Here is what happens on a single page load.

  1. Disabled check. cosmeticFilter.ts reads effective settings from a per-page cache. If protection is paused for this host, it returns — nothing injected.
  2. Ask for the slice. It sends get-cosmetic-slice { hostname } to the service worker (one retry, then it degrades gracefully). The reply carries this host’s domainSelectors, the merged injectRules, the genericHigh list, and a hasTokenIndex flag — all with this domain’s exceptions already subtracted.
  3. Merge local selectors. The user’s own element-picker rules, custom hides, and the live cosmetic-fix channel are added on top — these live in storage.local, cost nothing to read, and are applied even if the slice request failed.
  4. Inject three <style> blocks. #moat-cosmetic-domain (domain + custom + gray), #moat-cosmetic-inject (CSS-injection rules, each with its own declaration), and #moat-cosmetic-generic (the genericHigh slice). Selectors are batched 2,000 to a rule rather than one enormous list.
  5. Start the surveyor — only if hasTokenIndex. A batched MutationObserver watches class and id attributes, hashes each new token, and once every 250 ms sends the new hashes as get-cosmetic-generics { hashes[] }. Returned selectors are appended to the -generic block. It stops itself after 8 consecutive empty flushes or 100,000 surveyed nodes.
05

Why the worker owns the dataset

Before v0.11.63, cosmeticFilter.ts did the fetching and JSON.parse itself, on the page’s main thread, at document_start — the moment the page most needs that thread for its own parsing and first paint. That was ~684 KB of JSON for the meta file plus 1–3 domain-bucket shards at ~110 KB each: roughly a megabyte of parse work per navigation, every navigation.

v0.11.63 moves it. background/cosmeticIndex.ts fetches and parses each file once and keeps the parsed structure in worker memory. The page just sends two small messages and gets selectors back.

Stays on the page thread

  • Two runtime.sendMessage round-trips — ~1–5 ms against a warm worker
  • Building and appending the <style> text (dozens–hundreds of selectors)
  • The MutationObserver survey loop & token hashing
  • Reading the user’s own picker / custom / live-fix selectors from storage.local

Moved to the service worker

  • fetch + JSON.parse of cosmetics-meta.json — ~684 KB
  • fetch + JSON.parse of the domain-bucket shards
  • Merging shards, resolving the domain chain, subtracting exceptions
  • Token-hash → selector lookup for the surveyor

Warm worker vs. cold start

While you’re actively browsing, the worker stays alive and the parsed index is already resident — the message round-trip is a few milliseconds. After the worker has been idle long enough to be killed, the first get-cosmetic-slice wakes it and it re-parses lazily. That’s comparable to the old cost, except the page thread is waiting on a promise rather than burning CPU itself — and the genericByHash map never touches the page at all.

Graceful degradation

If both message attempts fail (the worker restarting mid-flight), the page still applies the user’s own selectors and the live-fix channel. Only the bundled-list slice is lost for that one load — the same visible outcome as a failed fetch before, but now the user’s rules no longer share that failure path.

One less fingerprint

The worker reads the dataset through runtime.getURL from its own context, so rules/cosmetics-*.json no longer needs a web_accessible_resources entry. Dropping it closes a directly-probeable chrome-extension://<id>/rules/cosmetics-meta.json — a URL any page could fetch to detect Moat. consent-rules.json and ad-networks.json, still read from content scripts, stay listed.

06

What stayed, what’s deferred

This is the partial form of a larger idea. The full version — mirroring uBlock Origin Lite — would have the worker compute selectors on webNavigation.onCommitted and inject them with scripting.insertCSS from the worker, leaving the content script running only the surveyor.

That stayed deferred on purpose. From the current baseline it only changes where the <style> goes, for a small gain, against real cost: insertCSS from onCommitted is only roughly document_start-class timing (a first-paint race), undoing it needs an exact { css, origin } match and per-tab bookkeeping, and the cross-browser origin: "USER" behaviour has its own quirks. The partial split already took the megabyte of parsing off the page thread — the expensive part — with none of that risk.
